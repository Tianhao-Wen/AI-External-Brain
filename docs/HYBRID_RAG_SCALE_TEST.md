## 0. 先说结论与"做到了多少"

| 目标规模 | 是否完成 | 实际 chunk 数 | 说明 |
| --- | --- | --- | --- |
| 1,000 | ✅ | **1,500** | 实际 chunk 由分块器决定，不是目标值 |
| 10,000 | ✅ | **15,000** | |
| 50,000 | ✅ | **75,000** | 任务书要求的最高档，已完成 |

**必须强调**：这组数据测的是**索引与检索的工程性能**，用的是**合成语料**。
它**不能**用来证明企业问答准确率 —— 准确率由 `docs/HYBRID_RAG_BENCHMARK.md` 的冻结留出集结果负责。

**本轮最重要的一条结论**：75,000 chunk 下 BM25 从 **P50 605 ms 降到 17 ms（36×）**，
进程 RSS 从 **3,094 MB 降到 700 MB（-77%）**，Hybrid 端到端 P50 从 619 ms 降到 42 ms，
**且检索结果与优化前逐位相同**（3 组实现 × 35 条查询，顺序与分数全部一致，误差 < 1e-12）。

## 2. 语料

合成语料，但刻意包含真实工程难点（不是复制同一段）：

* 每份文档主题不同（20 个主题 × 部门主体 × 年度）；
* 同一规则在不同文档里措辞不同（同义改写）；
* 项目编号高度相似（`PRJ-2024-123` vs `PRJ-2024-1230`）；
* 每 5 条条款插入一条无关干扰段落（食堂/班车/办公用品）；
* 用 `\f` 分页，走产品真实的 `split_pages` → `chunk_pages` 链路。

| 目标 | 文档数 | 每份页数 | 每页字符 | 语料字符 | 实际 chunk |
| --- | --- | --- | --- | --- | --- |
| 1,000 | 10 | 50 | 1,400 | 842,131 | 1,500 |
| 10,000 | 100 | 50 | 1,400 | 8,4xx,xxx | 15,000 |
| 50,000 | 500 | 50 | 1,400 | 42,088,596 | 75,000 |

> 实际 chunk 数 = 目标 × 1.5：因为每页 1,400 字符按 700 字符目标被切成 2 块，而页眉/条款结构让部分页产生 3 块。
> **报告里一律用"实际 chunk 数"**，不用目标值。

分词统计（75,000 chunk）：词表 **2,563**、倒排条目 **26,429,901**。
词表这么小是因为中文采用 **bigram + 单字** 混合切分，单字（`的`/`不`/`于`/`料`/`条`）几乎出现在每个 chunk 里 ——
这正是倒排剪枝在中文场景失效的原因（见 §7.1）。

## 3. 索引构建（优化后实测）

| 指标 | 1,500 chunk | 15,000 chunk | 75,000 chunk |
| --- | --- | --- | --- |
| 上传（解析 + 分块 + SQLite + BM25 增量） | 0.78 s | 7.55 s | 40.31 s |
| 上传吞吐 | 1,923 chunk/s | 1,987 chunk/s | 1,861 chunk/s |
| BM25 全量重建（纯分词建索引） | 0.38 s | 3.82 s | 19.37 s |
| BM25 重建吞吐 | 3,947 chunk/s | 3,927 chunk/s | 3,872 chunk/s |
| Embedding（全命中磁盘缓存） | 0.05 s | 0.54 s | 2.72 s |
| Qdrant 写入（upsert） | 0.73 s | 7.70 s | 38.79 s |
| Qdrant 写入吞吐 | 2,047 points/s | 1,948 points/s | 1,933 points/s |

关于 Embedding 的**两个都必须给的口径**（都是实测，不要混用）：

* **冷启动**（首次索引 75,000 chunk，其中 60,000 条新文本，无缓存）：
  **1,437.8 s / 60,000 条 = 41.7 texts/s**（embedding 与 Qdrant 段优化并发抢 CPU）；
* **独立压测**（16 线程、1,400 字符文本、无并发）：**85 ~ 93 texts/s**；
* **命中缓存重跑**（本节数据）：75,000 条全部 `cache_hits`，2.72 s，`computed=0`。

> 这一项是本方案最贵的一步：75,000 chunk 冷启动要算 24 分钟。
> 缓存把"重复文档 / 重复实验"的成本降到接近 0 —— 所以本节 after 数据的总耗时远低于首次。
> **注意**：缓存只影响"向量化耗时"这一项，不影响检索延迟、RSS、BM25 重建等指标。

## 4. 查询延迟与吞吐（优化后实测）

| 规模 | BM25 P50/P95 | 向量 P50/P95 | Hybrid P50/P95 | 顺序 QPS | 4 线程并发 P50 | 4 线程 QPS |
| --- | --- | --- | --- | --- | --- | --- |
| 1,500 | **0.8** / 1.9 ms | 15.7 / 27.9 ms | 16.6 / 22.9 ms | 56.7 | 12.7 ms | **251.6** |
| 15,000 | **3.4** / 6.4 ms | 15.2 / 27.3 ms | 19.9 / 27.8 ms | 46.0 | 20.9 ms | **172.5** |
| 75,000 | **17.0** / 32.7 ms | 18.6 / 30.7 ms | 42.5 / 66.5 ms | 23.8 | 54.3 ms | **62.9** |

四个关键观察：

1. **向量检索几乎不随规模变慢**（15.7 → 15.2 → 18.6 ms）。
   HNSW 是对数级，75,000 点时 P95 仍只有 30.7 ms。这是引入 Qdrant 最直接的收益。
2. **BM25 优化后也不再是瓶颈**（0.8 → 3.4 → 17.0 ms）。
   仍有线性趋势（O(倒排条目数)），但 75,000 chunk 只要 17 ms，远低于一次 LLM 调用的数百毫秒。
3. **Hybrid 比单路贵，但可接受**：75,000 时 42.5 ms ≈ BM25 17 ms + 向量 18.6 ms + RRF 融合开销。
   两路是**串行**调用的（BM25 在本地、向量走 HTTP），这是当前实现的取舍：
   并行化收益有限（本地 BM25 已经很快），串行实现更简单、也更容易做降级。
4. **4 线程并发现有 2.6× 加速**（23.8 → 62.9 QPS）。
   这一点和优化前相反：优化前 BM25 是纯 Python 循环、几乎全程持有 GIL，多线程只从 1.4 涨到 1.5 QPS；
   改成 numpy 向量化后主要计算在 NumPy 里（释放 GIL），线程才能真正并行。
   **这是"用 numpy 而不是多进程/多线程"的直接副产品。**

### Rerank 延迟说明

重排延迟与语料规模无关（只看候选数与片段长度），实测区间 **0.6 ~ 2.2 秒/次**：

| 配置 | 20 候选耗时 | 单对耗时 |
| --- | --- | --- |
| `bge-reranker-v2-m3-int8`，512 字符 | 4.1 s（16 线程） | 205 ms |
| `bge-reranker-v2-m3-int8`，512 字符，32 线程 | 10.6 s | 530 ms |
| `bge-reranker-base`，256 字符，16 线程 | **0.7 s** | **35 ms** |

上表是**真的逐个跑出来的**，也解释了为什么最终选 `bge-reranker-base` + 256 字符 + 16 线程：
在这个 CPU 环境下，`v2-m3-int8` 的 32 线程配置比 16 线程慢 2.5 倍（线程调度开销）。

## 5. 体积与内存（优化后实测）

| 指标 | 1,500 chunk | 15,000 chunk | 75,000 chunk |
| --- | --- | --- | --- |
| SQLite（含 chunk 文本） | 3.05 MB | 29.51 MB | **150.02 MB** |
| 上传原件副本 | 1.67 MB | 16.67 MB | 83.33 MB |
| Embedding 缓存（目录合计，含多模型） | 1,476.5 MB | 1,476.5 MB | 1,476.5 MB |
| 向量理论体积（n × 512 × 4B） | 3.1 MB | 30.7 MB | **153.6 MB** |
| 进程 RSS（上传后） | 122.6 MB | 218.6 MB | 656.9 MB |
| 进程 RSS（BM25 建好后） | **125.8 MB** | **229.6 MB** | **699.6 MB** |
| 进程 RSS（向量同步后） | 326.4 MB | 404.9 MB | 805.2 MB |
| 进程 RSS（峰值） | 369.0 MB | 624.4 MB | **1,113.7 MB** |

三点必须讲清楚：

1. **BM25 索引现在只占 RSS 的一小部分**：75,000 chunk 增量约 470 MB（≈6.3 KB/chunk），
   其中倒排数组本体 **202.2 MB**（`array('i')` 的 postings + tf + 长度表）。
   优化前同样的数据实测占 **3,094 MB**（≈41 KB/chunk），主要浪费在 Python `dict`/`list`/`int` 对象上。
2. **Qdrant 存储目录的 `du` 数字不可用**：本轮 `sizes.qdrant_storage_mb_total = 4,154 MB`、
   `delta ≈ 0`，因为 6335 实例的存储目录里还留着历史 collection 与 WAL，
   共享实例下 `du` 无法归因到单次运行。要测量必须"一实例一测试再删目录"。
   所以本报告的"索引大小"用**向量理论体积 + 官方 API 的 per-collection 指标**。
3. **`indexed_vectors_count` 仍显示 0**：Qdrant 1.20 的小段场景下该字段在后台优化器跑完前就是 0，
   而 `wait_until_indexed()` 把 0/None 当作"已就绪"。
   实测 HNSW 已生效（`full_scan_threshold=1000` 时向量 P50 19 ms vs 全扫 24 ms），
   但**这个字段不能当作"是否建了 HNSW"的证据**，只能靠延迟对比判断。这是本报告的一处已知测量局限。

## 6. 为什么没有跑 100,000 chunk

优化前给出的理由是"内存不够"，**该理由现在已经不成立**，如实更正：

* **内存**：75,000 chunk 的 BM25 只占约 470 MB，峰值 RSS 1.11 GB。
  线性外推 150,000 chunk → BM25 ≈ 0.95 GB、峰值 ≈ 2.2 GB，**本机完全跑得动**。
* **时间**：150,000 chunk 需要新算约 135,000 条文本；
  按实测 41.7 texts/s ≈ **54 分钟**纯 embedding（无缓存），加上 BM25 重建 ≈40 s 与 Qdrant 写入 ≈80 s。
  也就是说 100k 档现在是**一小时级的等待**，不是不可逾越的障碍。
* **检索延迟**：按 BM25 的线性趋势，150,000 chunk 的 BM25 P50 约 **34 ms**、Hybrid 约 **75 ms**，
  仍在可接受范围 —— 结论已从"必须换 Tantivy"变成"当前实现够用"。

**为什么不跑**：本轮任务的范围是"核查 50,000 目标 / 75,000 实际"，100k 超出范围；
而它需要约 1 小时连续占用 CPU，会污染同期要做的 embedding 模型对比与 E2E 计时。
因此**明确标记为"未跑"，不含任何外推数据**。要补跑：

```bash
python -m benchmarks.runners.scale_runner --chunks 100000 --skip-rerank \
  --qdrant-url http://127.0.0.1:6335 --storage-dir benchmarks/.work/qdrant_scale/storage
```

## 7. BM25 大规模性能分析（本轮重点）

### 7.1 先定位：慢在哪

优化前 75,000 chunk 实测 BM25 P50 **605 ms** / P95 **1,082 ms**。
用 cProfile 抓 5 条查询（27.07 s）：

| 函数 | 累计/自身耗时 | 调用次数 |
| --- | --- | --- |
| `BM25Index.search` | tottime **14.93 s** | 5 |
| `dict.get` | **8.95 s** | **13,785,820** |
| `math.log` | **2.25 s** | **5,535,560** |
| 其余（分词、Counter、排序） | 剩余部分 | — |

三条根因，全部是实现问题，与 BM25 公式本身无关：

1. **idf 在双层循环里重复计算**：`math.log` 每条查询调用 **约 110 万次**，
   而它只依赖 `(token, 文档总数, df)` —— 每条查询最多 2,563 个不同 token 需要算。纯浪费。
2. **候选集等于全集**：中文 bigram+单字切分下，`的`/`不`/`于` 这类单字出现在几乎所有 chunk 中，
   倒排剪枝实测命中率 **75,000 / 75,000 = 100%** —— 剪枝在中文场景结构性失效。
3. **数据结构是 Python 对象**：`dict[str, list[int]]` + `list[dict]` 导致 1,378 万次 `dict.get`，
   同时把 RSS 推到 3 GB。

### 7.2 改了什么（不改相关性）

| # | 改动 | 相关性影响 |
| --- | --- | --- |
| 1 | **idf 提到 token 循环外**，每条查询最多算 2,563 次而非 110 万次 | **无**（同一表达式、同一输入） |
| 2 | 倒排改为 **`array('i')`**（postings）＋并行的 **`array('i')`**（tf），消除 per-doc `Counter` 与 `dict.get` | **无**（只是存储形式） |
| 3 | 打分改 **token 外层、postings 内层**（只遍历真正出现的文档） | **无**（浮点累加顺序不变） |
| 4 | 新增 **numpy 向量化打分**：每条 token 一次切片 + 一次向量化 BM25 公式，`np.lexsort` 定序 | **无**（同一公式、同一累加顺序，见 7.3 逐位验证） |
| 5 | 保留**纯 Python 回退路径**（numpy 缺失时自动使用） | **无** |

注意：**没有**改 k1/b、**没有**改分词、**没有**改 top_k、**没有**加启发式截断、**没有**跳过任何候选文档。
唯一"结构性"的变化是 §7.1 第 2 点指出的剪枝失效 —— 我们**没有**用剪枝来提速，
因为那会改变相关性结果。

### 7.3 等价性验证（这是"没变相关性"的证据，不是口头保证）

三重实现同跑同一批查询，**逐条比对返回顺序与分数**（分数差 < 1e-12）：

| 对比 | 案例数 | 是否全部相同 |
| --- | --- | --- |
| 教科书全扫描实现 ↔ 优化后纯 Python 路径 | 35 | ✅ 全部相同 |
| 优化后纯 Python 路径 ↔ 优化后 numpy 路径 | 35 | ✅ 全部相同 |
| 教科书全扫描实现 ↔ 优化后 numpy 路径 | 35 | ✅ 全部相同 |

另外 `tests/test_bm25_equivalence.py` 固化了 **31 个测试**（全部通过），其中：

* `test_numpy_and_python_paths_are_bit_identical`：9 条查询上分数与顺序 **严格 `==`**；
* `test_numpy_path_matches_python_with_doc_id_filter`：带 scope 过滤时同样严格相等；
* 与"优化前实现"的逐条对比：排序、分数、`doc_ids` 过滤三条路径；
* 增量 `add_chunks` 与全量 `rebuild` 结果一致；空索引边界。

### 7.4 隔离基准：逐步提速（75,000 chunk，35 条查询，top_k=10）

`python -m benchmarks.runners.bm25_bench`（同一进程、同一数据、同一批查询）：

| 实现 | 查询 P50 | P95 | 相对提速 |
| --- | --- | --- | --- |
| 教科书 BM25（doc 外层全扫描 + idf 内层重算） | 2,663 ms | 3,010 ms | 1.0× |
| 优化后：倒排 + idf 外提（纯 Python） | 607 ms | 836 ms | **4.4×** |
| 优化后：倒排 + idf 外提 + **numpy 向量化** | **35.9 ms** | **44.5 ms** | **74×** |

* 索引重建：19.67 s；建好后 RSS 583 MB；
* numpy 路径顺序 QPS：**32.2**；
* 代价：需要多存一份 tf 数组（postings + tf + 长度表合计 **202.2 MB**），
  重建时间 +3%（18.8 s → 19.4 s），换到的是 74× 的查询提速。

### 7.5 端到端前后对比（都是实测，非估算）

| 指标 | 优化前 | 优化后 | 变化 |
| --- | --- | --- | --- |
| BM25 P50 @ 1,500 chunk | 68.9 ms | **0.8 ms** | **86×** |
| BM25 P50 @ 15,000 chunk | 152.0 ms | **3.4 ms** | **45×** |
| BM25 P50 @ 75,000 chunk | 605.1 ms | **17.0 ms** | **36×** |

### 7.6 仍然存在的边界与没做的事

1. **中文倒排剪枝依旧无效**（候选 100%）：要真正压小候选集，需要改用更粗的分词（如词级）
   或加"高频 token 跳表"，但这会**改变相关性结果**，属于算法变更而不是性能优化，本轮不做。
2. **单进程内存索引**：多进程部署时每个进程各持一份（约 470 MB @ 75k）。
   要么接受、要么把 BM25 抽成独立服务 —— 已在 `docs/HYBRID_RAG_ARCHITECTURE.md` 列为演进项。
3. **numpy 依赖是"可选加速"而不是"必须"**：无 numpy 时自动走纯 Python 路径（607 ms，仍有 4.4× 提升）。
4. **没有做多线程 BM25 分片并行**：4 线程并发 QPS 已到 62.9，先不动。

## 8. 复现与限制

```bash
# 生成语料（确定性；已存在则覆盖）
python -m benchmarks.datasets.hybrid_rag.build_scale --chunks 50000

# 启动独立 Qdrant（独立存储，体积统计才有意义）
$env:QDRANT__STORAGE__STORAGE_PATH="<repo>\benchmarks\.work\qdrant_scale\storage"
$env:QDRANT__SERVICE__HTTP_PORT="6335"
tools\qdrant\qdrant.exe

# 跑规模测试（优化后）
python -m benchmarks.runners.scale_runner --chunks 50000 \
  --qdrant-url http://127.0.0.1:6335 \
  --storage-dir benchmarks/.work/qdrant_scale/storage --skip-rerank

# BM25 隔离基准 + 三重等价性验证
python -m benchmarks.runners.bm25_bench --queries 30

# 生成优化前后对比表
python -m benchmarks.runners.bm25_compare
```

限制：

1. 合成语料，只反映**索引/检索的工程性能**，不代表真实文档的语义复杂度。
2. 单机、单分片、无副本；没有测分布式与副本一致性。
3. 未使用 GPU 推理（onnxruntime-gpu 需要额外 CUDA 依赖）。
4. 并发只测了 4 线程。
