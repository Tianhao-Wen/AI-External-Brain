## 3. 根本原因

1. **Prompt 只说了"要抽出风险"，没说"什么不算风险"**。
   模型把"提到不利词汇"等同于"存在风险"，对否定、已解决、假设、要求、总结这些
   语义没有约束。这是精度低的**主因**（实验证明：只改 Prompt 就能把开发集 Precision
   从 64.1% 提到 92.0%）。
2. **缺少可执行的判定标准**，等级全凭感觉，导致中风险被系统性抬高。
3. **Agent 不知道知识库里有什么**。工具描述说"可以检索",但环境上下文里没有文档清单，
   模型无法判断"这个问题该不该查"，于是反问用户——这是环境状态缺失，不是 Prompt 措辞问题。
4. **PPT 页数是"事后追认"而非"硬约束"**：封面页与总结页固定追加，页数不做裁剪，
   返回值还漏算了表格页。
5. **引用缺少校验**：模型把"检索到的上下文页"当成"引用"全部标上。

## 4. 技术解决方案

### 4.1 会议风险：Prompt 判定标准 + 确定性校验（两层）

**第一层：把"什么算风险"写成可执行的判定条件**（`aieb/brain/meetings.py::ANALYSIS_SYSTEM`）

* 必须同时满足：(a) 原文写出了一件已存在或明确将发生的不利事实；(b) 尚未解决；
  (c) 依据里能读到这件事实本身，而不只是"要小心/需要评审"这类要求；
* 明确列出 7 类不该报的情况（已解决、规范提醒、背景说明、假设、待评估、已撤回决议、同一事实拆分）；
* 增加 `risk_type` 与 `status(open|resolved|uncertain)` 两个结构化字段；
* severity 给出 high/medium/low 的**锚点定义**，禁止把已解决事项标为 high。

**第二层：确定性校验**（新增 `aieb/brain/risk_rules.py`，11 个单测）

* 依据为空 → 丢弃（不可核查的风险正是误报来源）；
* 依据或**依据的下一句**含"已解决/已恢复/已关闭/未复现"且无"尚未/仍未" → 丢弃；
* 依据只由指令词（提醒/要求/必须/不要/应当）构成，且标题+描述+依据里都没有问题词 → 丢弃；
* 假设词 + 测算词同时出现 → 丢弃；
* 待评估标记 → 丢弃；总结标记（以上问题/综上/叠加）→ 丢弃；
* 同一 `risk_type` 且关键短语高度重合 → 合并，保留更严重的一条；
* 每条丢弃都带 `dropped_reason` 并写日志，可逐条复核。

### 4.2 Agent 知识库路由：补状态 + 轻量路由提示（不是改 Prompt 措辞）

* `BrainService.knowledge_context()`：把**当前知识库有几份文档、分别是什么**注入 Agent 的
  环境上下文（`Agent.set_env_context_extra`，由 `remote._init_agent` 在生产端接入）；
* 新增 `aieb/brain/routing.py`：对"制度/数据类事实问题"做规则判定（数量/比例/周期/条款… +
  企业语境），命中时**仅当轮**注入一句"先检索再回答"的系统提醒；闲聊、翻译、写作不注入，
  避免把所有问题都拖进 RAG；可用 `AIEB_KB_ROUTING=off` 关闭以做消融；
* 强化 Prompt：区分"该查"（公司制度/项目数据/金额比例）与"不必查"（闲聊/写作/用户已给全材料）。

### 4.3 PPT：把页数变成硬约束

* `render(..., total_slides=N)`：封面 1 页 + 总结 1 页固定，剩余预算分给内容页与可选表格页，
  内容页超出即裁剪；表格页只有在"还能留下至少 1 页内容"时才插入；
* 生成后**重新打开文件数页数**，`slide_count` 一律以文件为准（原来漏算表格页，回报 8 实际 9）；
* `generate()` 优先使用调用方传入的页数，只有缺省时才从主题文字里解析"N 页"；
* Benchmark 的 PPT 断言随之从"区间"收紧回**精确页数**（8/5/10/6）。

### 4.4 RAG 引用：尝试了三种方案，最终**未采纳**

| 方案 | 开发集 引用准确率 / 答案正确率 | 结论 |
| --- | --- | --- |
| 基线 | 0.894 / 0.967 | — |
| 收紧 Prompt（不写补充说明、只答小问） | 0.944 / 0.900 | 引用↑但答案↓，不可接受 |
| 收紧 Prompt（答全小问 + 只标必要页） | 0.900 / 0.933 | 引用无稳定提升 |
| 生成后确定性引用剪枝（`prune_citations`） | 0.911 / 0.933 | 会误删正确引用（引用覆盖率 0.956→0.911） |

**决定：保持原 Prompt 不变**，只做了一处无风险的工程收敛（把重复的内联提示提取为
`ANSWER_SYSTEM` 常量，`ops.py` 与 `service.py` 共用）。
`knowledge.prune_citations` 的实现与 6 个单测保留在仓库中，**默认关闭**
（`AIEB_CITATION_PRUNE=1` 可开启），供后续把支撑度判定做准后再启用。

## 7. 检索准确性与引用质量

* **检索层未改动**，Recall@5 在三个切分上完全一致（0.956 / 0.964 / 1.000）。
  这是有意的：检索不是本次瓶颈，动它只会引入噪声。

* 保留的产出：`prune_citations` 的实现、6 个单测、以及"引用指标必须从回答正文解析"这一

## 9. Agent 任务成功率变化

* **开发集 +5.9pt（15/17 → 16/17）**，其中知识库路由修复使 A2/A4 由失败转通过。
* **已暴露测试集 −12.5pt（8/8 → 7/8）**：唯一失败是 G2，模型改用 Bash/ReadFile 探查 CSV
  并给出"可以做两件事"的选项，没有说出断言期待的"不支持该格式"。
  从行为看这次回答并不差，属**断言关键词过窄**造成的假阴性；因该题位于已暴露测试集，
  按"不在测试集上调参"的原则**没有修改断言**，如实记在这里。
* **未暴露测试集 0pt（5/6 → 5/6）**：UA6（英文回答）已修复，UA4（PPT 缺素材时仍拒绝生成）
  仍失败——说明"缺素材也要生成"这条指令在陌生表述下并不可靠。
* **延迟全面下降**：P50 −9%~−31%，P95 −11%~−19%，平均 LLM 调用在已暴露集从 3.50 降到 2.88。

这两项是下一步的主要方向（见 §12）。

## 12. 剩余问题与局限性

**仍然失败/未达标的：**

1. **PPT 任务成功率没有实质提升**（dev 50%、unseen 0%）。页数问题已修，剩"是否生成"
   与"调用次数过多"两个问题。
2. **Agent 任务成功率未达 95% 目标**：dev 94.1%、exposed 87.5%、unseen 83.3%。
   小样本下每条任务权重 6–12 个百分点，95% 这个目标本身在此规模上不具备统计意义。
3. **会议 Recall 从 100% 降到 92%**（开发集 2 条），原因是模型把"资源约束"并入主风险。
4. **RAG 引用准确率仍是 89% 左右**，多数是"多引了相邻页"，现有手段（Prompt / 剪枝）
   在 ±4pt 噪声下都无法证明有效。

**方法论局限：**

* 会议 dev 25 条风险、Agent 每个切分 6–17 个任务，**单条样本权重极大**；
  本文所有百分点变化都标注了分母，但小样本差异不宜过度解读。
* `test_exposed` 虽然与 dev 分开，但它在搭建评测体系时被反复看过（改过标注与断言），
  严格意义上只能算"半独立"。`test_unseen` 是唯一完全干净的数据。
* 未暴露 RAG 集基线即满分（1.000），说明其区分度不足，只能用于回归检测。
