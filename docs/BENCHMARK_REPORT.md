## 1. 评测目标与范围

**目标**：用可复现的量化方式回答三个问题，而不是"跑通一个 demo"。

1. 文档问答：检索能否把证据找全？回答是否忠于原文？没有答案时会不会编？
2. 会议分析：能不能把风险、待办、决策抽干净？会不会虚报、会不会编造负责人？
3. 端到端 Agent：用户用自然语言提需求，系统能不能真的把事办成（生成文件、发邮件、跨会话回忆）？

**不评测**：UI 视觉、并发/多用户性能、真实互联网信息时效性、模型本身的通用能力。

**被测对象**：项目内的 `aieb` 包（知识库 BM25 检索、会议结构化抽取、Agent 工具循环），
以及它背后的模型提供方（DeepSeek `deepseek-chat`）。

## 2. 被测系统架构与评测切入点

```
用户自然语言
   │
   ├─ 业务层 BrainService ── upload() → 解析(PyMuPDF) → 页内分块(700/120) → BM25 索引
   │        │                search()  → Top-K 片段
   │        │                answer()  → 拼上下文 → LLM → 带 [来源：文档·第N页] 的回答
   │        │                analyze_meeting() → LLM 结构化抽取 → sanitize(依据校验) → SQLite
   │
   └─ Agent 层 Agent ── LLMClient.stream() → tool_calls → ToolRegistry → 8 个业务工具
```

评测**全部从公开接口进入**：`BrainService.upload / search / answer / analyze_meeting / send_email`、
`Agent.run_to_completion`。没有为了评测新增任何"仅测试可见"的旁路，也没有改动业务流程，
唯一的插桩是**工具实例包装**（记录每次调用是否异常）与 **LLM 调用计数**，两者都不改变执行语义。

## 3. 评测方法与隔离机制

| 维度 | 做法 |
| --- | --- |
| 数据隔离 | 每次运行新建 `benchmarks/.work/<run_id>/workspaces/<suite>/`，`BrainService(work_dir=…)` 在其中生成独立 SQLite、会话、记忆、上传与产物目录 |
| 正式数据保护 | 运行起止各取一次项目 `.aieb/` 的目录指纹（文件名+大小+mtime 的 SHA256 前 16 位），不一致则以退出码 2 报警；三次运行均为「未被改动」 |
| 邮件安全 | 清空 `*_SMTP_*` 环境变量 + 强制 `AIEB_EMAIL_DRY_RUN=1` + 把 `mailer.send_email` 换成 Fake SMTP 记录器；三轮共 0 封真实投递 |
| 调用预算 | `--max-calls` 同时拦截业务层 `llm.complete` 与 Agent 主循环的 `LLMClient.stream`；超限抛 `BudgetExceeded`，已产出的样本仍旧落盘 |
| 失败处理 | 单题异常 → 记一条全 0 样本（保留在分母），不 continue |
| 密钥 | 元信息只记 provider 名/模型名/端点主机；落盘文本统一过脱敏 |

## 4. RAG 数据集设计

4 份**虚构**企业 PDF，共 20 页，覆盖三种文档语气（管理制度 / 技术规范 / 项目计划 / 信息安全规定）：

| 文档 | 页数 | 内容 |
| --- | --- | --- |
| DOC-A 内部管理手册 | 6 | 采购审批门槛、差旅报销、用印流程、合同签署 |
| DOC-B 供应商质量管理规范 | 5 | 评分分级、来料检验、不合格处理、审核 |
| DOC-C 星海项目预算与交付计划 | 5 | 预算构成、里程碑、变更控制、预备费 |
| DOC-D 信息安全与数据分级规定 | 4 | 四级密级、外发加密、权限有效期 |

题目 50 道，9 种题型（题量控制在既能区分能力、又能人工复核的规模）：

| 题型 | 题数 | 考察点 |
| --- | --- | --- |
| single_page | 8 | 单页事实定位 |
| multi_page | 6 | 跨页整合 |
| multi_condition | 6 | 多条件组合（金额/季度/密级） |
| numeric | 6 | 数值精确性 |
| cross_document | 5 | 跨文档联合推理 |
| negative | 6 | 资料里没有，必须拒答 |
| paraphrase | 5 | 口语化改写，考察语义匹配而非字面匹配 |
| long_distractor | 4 | 长文档中的干扰段落 |
| page_citation_trap | 4 | 同主题在多页出现，考察引用页码是否精确 |

**数据集自检**（`validate_dataset.py`，退出码非 0 即失败）：
标准证据页必须存在且题面确实落在该页；答案关键词必须能在标准页原文中找到；
禁用词必须在标准页中不存在。当前 **50/50 通过**。

## 6. 会议数据集设计

33 场**虚构**会议（人名、公司、金额全部编造），覆盖真实会议里最容易出错的结构：

| 类别 | 场次 | 设计意图 |
| --- | --- | --- |
| single_risk | 11 | 单一风险，考察基础抽取 |
| multi_risk | 7 | 2–3 条不同风险的区分与拆分 |
| no_risk | 10 | **纯负例**：通篇无风险，考察会不会虚报 |
| resolved_trap | 1 | 上次的风险"已经消除"，考察会不会把已解决事项当风险 |
| negated_decision | 1 | 原定全量发布改为灰度，考察能否抓住最终结论 |
| retracted_decision | 1 | 明确"撤销上次决议"，考察会不会把旧结论当最终结论 |
| missing_owner | 1 | 原文没写负责人，考察会不会编造 |
| missing_deadline | 1 | 原文没写截止时间，考察会不会编造 |

标注规模：**40 条风险**（8 类：进度/成本/质量/技术/资源/需求变更/合规/供应商）、
**75 条待办**、**65 条决策**。其中 1 条待办的负责人、4 条待办的截止时间**故意留空**，
用来检验"原文没有就必须留空"这条硬约束。

**标注口径**（写进数据集文档与自检脚本）：每条形如"问题/隐患/缺口"的明确表述标为一条风险；
同一主题的多个侧面合并为一条，模型若拆成多条，超出部分按细分重复计入误报。
所有判分关键词必须原样出现在正文中，`build_dataset.py` 逐条校验，不通过即 `exit 1`。

**匹配方式**：一对一贪心匹配（按命中短语数降序指派，每个标准项与每个预测项最多匹配一次），
因此"把一条风险拆成三条"不会提高召回、只会增加误报。

| Recall | **97.5%** |

## 8. Agent 任务设计

25 个任务，7 类能力，全部用自然语言描述，断言只检查"结果对不对"：

| 类型 | 任务数 | 覆盖 |
| --- | --- | --- |
| A. PDF 问答 | 4 | 数值问答、跨题引用、无答案拒答 |
| B. 会议风险分析 | 4 | 有风险/无风险/待办/否定式决策 |
| C. 跨会话记忆 | 4 | 结论回忆、责任人回忆、议题回忆、无记录如实说 |
| D. 联网搜索 | 3 | 固定 fixture，考察"会不会调工具、用不用结果" |
| E. 邮件流程 | 3 | 生成草稿、明确禁止发送、人工确认后投递 |
| F. PPTX 生成 | 3 | 8/5/10 页，用 python-pptx 真打开校验 |
| G. 异常与多轮 | 4 | 文件不存在、格式不支持、知识库无文档、同会话两轮追问 |

几个关键设计：

* **两个成功率分开**：`tool_call_success_rate` 只说明工具没抛异常，`task_success_rate` 要求全部断言通过。
* **重复运行**：7 个任务标记 `repeat`，`--repeat 3` 时共 21 次执行，全部轮次进结果，并统计"全部轮次都通过"的比例。
* **Fake SMTP**：邮件任务的投递被替换成记录器，`email_not_sent` / `email_sent_count` 直接读记录器。
* **PPT 真校验**：用 python-pptx 打开产物，检查页数与每页可读文本，不看模型自己的说法。

### 9.2 失败样本（全部保留）

| 任务 | 现象 | 性质 |
| --- | --- | --- |
| A2 | 问"质量项占多少分"，模型回答"取决于你们的评分体系……要我查吗？"，**一次工具都没调** | 该查知识库却反问用户 |
| A4 | 问"公司股票代码"，模型直接说"你还没告诉我是哪家公司"，**未检索知识库** | 同上 |

这是产品层最值得改的一点（例如在系统提示里硬性要求"涉及公司制度/项目数据必须先检索"），
也解释了为什么第 5 节的 RAG 分数（95.5%）明显高于端到端问答成功率。

## 10. 可复现性与反作弊验证

### 10.1 同一命令可重复
`python -m benchmarks.run --suite rag --mode fixture` 两次运行的指标完全一致（检索层无随机性）；
live 模式的差异只来自模型采样，逐条样本都在 CSV 里可查。

### 10.2 隔离验证（每轮运行末尾自动打印）

| 校验项 | 结果 |
| --- | --- |
| 项目 `.aieb/` 指纹是否变化 | **三次运行均未变化** |
| 真实邮件是否发出 | **0 封**（Fake SMTP 记录 + dry-run 双保险） |
| 是否输出 API Key | 无（元信息仅 provider/模型/端点主机，正文统一脱敏） |
| 失败样本是否被剔除 | 无（每套件的分母 = 数据集全量） |

### 10.3 运行间波动（会议套件连跑两次）

| 指标 | 第 1 次 | 第 2 次 | 差值 |
| --- | --- | --- | --- |
| 风险 Precision | 62.3% | 65.0% | +2.7 pt |
| 风险 Recall | 95.0% | 97.5% | +2.5 pt |
| 风险 F1 | 75.3% | 78.0% | +2.7 pt |

## 11. 评测中发现的产品缺陷与薄弱环节

这些不是"评测没做好"，而是评测**发现的真实问题**，按严重程度排序：

1. **知识库未被可靠调用**（Agent A2/A4/F1#3）：模型会反问用户或直接说"没有资料"，而实际上
   知识库里就有答案。建议在系统提示中加入强约束，或在检测到"制度/项目/数值"类问句时强制预检索。
2. **风险等级系统性上浮**：中风险被抬成高风险 8 次，低风险从未被正确识别。
   对"按等级通知不同人"的流程有实际影响。
3. **无风险会议误报率 45.5%**：10 场无风险会议有 5 场被报出风险，其中包含"已消除""仍在可接受范围"
   这类被明确否定的表述。说明模型对否定/已解决语义的抵抗力不足。
4. **PPT 页数与请求不一致**：`CreatePresentation` 的工具描述称 `slides` 为"总页数（含封面）"，
   实际产物页数为"大纲页数 + 2"，请求 8 页得到 9 页。已在任务断言中按实际行为给出区间，
   并在报告的失败样本里记录了模型的自我说明。
5. **PPT 任务调用次数偏高**：单任务 12 次模型调用，主要消耗在多轮资料检索上，缺少"先规划再执行"的收敛约束。

> 以上问题均**未修改产品代码**（评测阶段只测量、不动被测系统）。修复建议与优先级已记录在此，
> 修复后可用同一套命令复测并对比。

## 12. 局限性

1. **样本规模有限**：RAG 50 题、会议 33 场、Agent 39 次执行。置信区间较宽，
   单点差异（例如 ±3 个百分点）不应过度解读。`需求变更` 类风险只有 1 条，其 P/R/F1 不具统计意义。
2. **数据集是自建的虚构语料**：真实性来自写作规范（制度语气、金额链、日期链、跨文档一致），
   但仍不等于客户真实文档。跨行业的泛化能力未测。
3. **没有使用 LLM-as-Judge**：所有判定都是确定性规则（关键词命中、页码集合、原型校验）。
   好处是任何人重跑都得到同样分数；代价是无法评估"表达是否自然、总结是否得体"。
4. **会议风险类型由评测侧规则分类器判定**：per-type Precision 受分类器影响（一致率 72.0%），
   报告已把该指标单独列出，主指标（召回/漏报）不依赖分类器。
5. **联网搜索使用固定 fixture**：D 类任务测的是"会不会调工具、用不用结果"，**不代表真实搜索质量**。
   真实网络受目标站点反爬与信息时效影响，本轮未纳入量化口径。
6. **单模型单次环境**：只测了 DeepSeek `deepseek-chat` 一种配置。换模型/换上下文窗口后需要重跑。
7. **Agent 的"成功"由断言定义**：断言覆盖了结果正确性，但没有覆盖"体验是否顺畅"（例如多问一句确认）。

## 附：一句话结论

在**不修改产品代码、不剔除失败样本、不发送任何真实邮件**的前提下：
文档问答端到端正确率 **96.0%**（拒答 6/6 全对）、会议风险抽取 **Recall 97.5% / F1 78.0%**、
待办抽取 **F1 98.7% 且 0 次编造负责人**、端到端 Agent 任务成功率 **89.7%**（工具调用成功率 96.6%）。
主要短板是**会议风险精度（65%）**与**知识库工具的路由可靠性**。
