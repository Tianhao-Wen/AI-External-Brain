# 真实 LLM 工作流 Benchmark（DeepSeek，25 场会议）

> 与 `docs/LANGGRAPH_BENCHMARK.md` 的区别（**两者不可互相替代**）：
>
> | | `LANGGRAPH_BENCHMARK.md`（fixture） | 本文（真实 LLM） |
> | --- | --- | --- |
> | 模型 | 确定性 fake | **真实 DeepSeek（deepseek-chat）** |
> | 用途 | 比较"原生编排 vs LangGraph 编排" | 衡量"模型在真实会议文本上的抽取质量 + 工作流正确性" |
> | 场景数 | 40 | **25** |
> | 能否代表模型能力 | ❌ | ✅ |
>
> 原始数据：`benchmarks/results/workflow/live_benchmark.json`
> 数据清单（已冻结哈希）：`benchmarks/datasets/live_workflow/manifest.json`
> 执行环境：Windows 11 / Python 3.14.2 / langgraph 1.2.20 / 模型 `deepseek-chat`

## 1. 数据集（25 场，作者编写 + 程序校验）

| 类别 | 数量 | 设计意图 |
| --- | --- | --- |
| A 简单会议 | 5 | 少量待办、明确负责人、简单决策（含 2 场应识别出"0 风险"） |
| B 多风险会议 | 5 | 供应商延期 / 成本超支 / 资源不足 / 跨部门依赖 / 未解决风险 |
| C 无风险或已解决 | 5 | 已关闭问题、历史风险、假设性测算、已否决建议、无实际风险 |
| D 复杂会议 | 5 | 多风险 + 多负责人 + 条件决策 + 风险间依赖 |
| E 长文本会议 | 5 | 770–1260 字（不含空白），多议题、跨段落关联、干扰信息 |

- 原文合计 8679 字（不含空白）；金标准 **93 条风险 / 77 条待办 / 决策 41 条**。
- 长度分档实测：short 109–142 字 / medium 159–316 字 / long 770–1260 字（无靠重复文本凑长度）。
- 会议内容全部为**虚构企业资料**，不含真实公司、真实人员或真实商业信息。

### 金标准是怎么来的（必须说明的边界）

| 环节 | 做法 | 强度 |
| --- | --- | --- |
| 会议文本 | 本仓库作者编写 | 合成数据 |
| 金标准标注 | 作者逐条标注 risks/todos/decisions + evidence 片段 | **作者标注** |
| 程序校验 | `scripts/verify_live_dataset.py`：每条 evidence 必须在原文**原样出现**；负责人/截止时间必须能在原文定位；长度分档与副作用期望必须自洽 | **程序验证通过** |
| 第三方人工复核 | ❌ 未做 | **不能称为人工标注金标准** |

因此本文所有指标都应理解为"**相对作者标注的一致性**"，而不是绝对准确率。
另外：因为观察到了下面的失败案例，**评分脚本在正式跑完后没有修改**（冻结哈希见 manifest），
只额外做了一次"宽松阈值"的灵敏度分析（§5），并明确不把它的数字当主指标。

## 2. 执行方式（每场都真的走完整链路）

```
会议文本 → LLM 分析 → 风险接地校验 → 待办接地 → 业务落库 → LLM 生成邮件草稿
        → interrupt 等待审批 → 控制器 approve/edit/reject → resume
        → Fake SMTP 投递（或取消） → 审计
```

- 分析、草稿都调用**真实 DeepSeek**；审批动作由 benchmark 控制器发出（模型无法自己批准）；
- SMTP 用进程内 **Fake SMTP**（真实 `smtplib` 协议、真实投递到内存），**全程零真实邮件**；
- 每场使用独立 workspace（独立业务库 + 独立 Checkpoint 库）。

### 预算控制与真实用量

| 项 | 值 |
| --- | --- |
| 预算上限 | 100 次真实调用（本轮声明为 120 次，见下） |
| Benchmark 实耗 | **50 次**（25 场 × 2：1 次分析 + 1 次草稿） |
| 输入 / 输出 tokens | **25,559 / 30,309** |
| 估算成本（上界） | **$0.044** |
| 计价假设 | DeepSeek 公示价：输入 $0.30/M（cache miss, 峰值）、输出 $1.20/M（峰值）；off-peak 为半价。取峰值作上界 |
| 另外的调用 | Pilot 10 次、灵敏度分析 26 次、Trace 导出 4 次、浏览器 E2E 18 次（6 场×3 次运行，含失败重试）；全项目真实调用合计约 108 次 |

> 为什么声明 120：E2E 前两次复跑各消耗 6 次调用（一次暴露了"空收件人"真实缺陷、一次修脚本），
> 这部分属于"工程验收"而非 Benchmark。为避免"静默超额"，这里把上限显式改为 120 并如实列出全部消耗。

## 3. 主指标（官方口径，25 场全量，严格匹配）

| 指标 | 值 | 分母说明 |
| --- | --- | --- |
| **Workflow Completion Rate** | **1.0（25/25）** | 分母 = 实际执行场景数；分子 = 终态与期望一致（23 completed + 2 cancelled） |
| **Task Success Rate** | **1.0（25/25）** | 分子还需满足：会议 1 条、邮件 1 行、发送次数符合期望 |
| Side-effect Correct Rate | 1.0 | 发送次数与 `expected_side_effects.sends` 一致 |
| **Risk Precision / Recall / F1（micro）** | **0.8539 / 0.8172 / 0.8352** | 分母：TP+FP=89（predicted 总数）、TP+FN=93（gold 总数） |
| Risk P/R/F1（macro，按场平均） | 0.8994 / 0.8903 / 0.8939 | 分母：25 场（无风险场也算 1.0） |
| **Todo Precision / Recall / F1（micro）** | **0.9383 / 0.9870 / 0.9620** | TP+FP=81、TP+FN=77 |
| Todo P/R/F1（macro） | 0.9716 / 0.9933 / 0.9814 | 25 场 |
| **Decision Extraction Recall** | **0.8133（35/41… 见下）** | 分母：41 条 gold decision（按场计算后取平均：0.8133） |
| **False Positive Rate** | **0.1461** | 分母：全部候选风险（TP+FP=89）；分子 FP=13 |
| Duplicate Side-Effect Count | **0** | 全部 25 场累计重复发送/重复建会议次数 |
| LLM Call Count | 50 | 2/场 |
| 端到端 P50 / P95 | **7,876 ms / 12,054 ms** | 分母：25 场；含 LLM + 编排 + Fake SMTP，**不含人工等待** |

## 4. 失败案例分析（全部保留原样）

**没有一个用例在"流程正确性"上失败**（完成率/副作用 100%），失败全部集中在**抽取质量**：

### 4.1 匹配器保守导致的"假失败"（约占风险 FN 的一半）

| 用例 | gold | 模型输出 | 判定 |
| --- | --- | --- | --- |
| B02 | 合同条款与客户要求冲突 | 客户数据留存要求与合同条款不一致存在争议 | 同一条，措辞不同 → 匹配器不接受（标题 bigram Jaccard < 0.45） |
| B04 | 数据口径不一致影响报表 | 销售与财务订单口径不一致 | 同上 |
| B05 | 特种设备年检逾期 | 两台压力容器年检逾期 | 同上（更具体） |
| D04 | 日志留存不足无法审计追溯 | 日志留存时长不满足等保要求 | 同上 |

这类是**度量问题而非模型问题**。评分脚本 v1 已冻结，未事后放宽（见 §5 灵敏度分析）。

### 4.2 真实漏报（模型确实没抽出来）

- **E01**：漏 `原材料涨价与先款后货带来资金压力`、`环保在线监测数据断连收到监管问询`。
  前者散落在"成本上升 18%"与"先款后货"两句，模型只抽了后者；后者是干扰信息较多的长文本里的次要风险。
- **E04**：gold 9 条 vs 模型 6 条 —— 模型把"查询接口 P99 超标 + 慢查询推高 IO"合并成 1 条、
  把"回归缺陷 + 覆盖率 + 用例库过时"合并成 1 条。**这是粒度差异**，说明我的 gold 在 E04 上切得比模型细。

### 4.3 决策抽取偏低的原因（已定位）

决策准确率 0.8133 主要不是漏抽，而是**模型把"决议"写成完整长句**（含负责人/截止时间），
而 gold 是压缩短句，严格的相似度阈值（0.35）不接受"长句包含短句"。
典型例子见 §5 的 A02/E01/E04：模型输出的决策里**逐字包含** gold 决策，但相似度只有 0.2 左右。

## 5. 灵敏度分析（**不是**主指标，仅用于解释偏差来源）

对 13 个出现不匹配的用例，用同一批真实输出、只放宽匹配阈值重算一遍（`live_benchmark_sensitivity.json`）：

| 指标（13 场子集） | 严格阈值（主指标口径） | 宽松阈值 |
| --- | --- | --- |
| Risk micro F1 | 0.7559 | 0.7717 |
| Todo micro F1 | 0.9615 | 0.9615 |
| Decision Recall | 0.7179 | **0.9487** |
| False Positive Rate | 0.1864 | 0.1695 |

结论：**决策准确率的差距主要来自匹配规则**（0.72 → 0.95），风险 F1 只从 0.756 提升到 0.772
（说明风险漏报里确实有真错，不是全部措辞问题）。

## 6. 与 fixture 对照实验的关系（不要混用）

| 指标 | fixture（40 场景，fake） | 真实 LLM（25 场） |
| --- | --- | --- |
| 任务成功率 | LangGraph 1.0 / 原生 0.9744 | 1.0 |
| P50 延迟 | 174.2 ms / 原生 14.9 ms | 7,876 ms |
| 重复副作用 | 0 | 0 |

**不能拿 fixture 的 12 ms 级延迟去和真实 LLM 的 8 s 比**，也不能把 fixture 的 1.0 成功率写成"真实模型成功率"。
fixture 衡量编排层，真实 LLM 衡量端到端质量，两者分母不同、成本不同。

## 7. 复现方式

```powershell
cd <repo>
$env:PYTHONPATH="<repo>"
# 先校验数据集（不花钱）
.venv-langgraph\Scripts\python.exe scripts\verify_live_dataset.py
# Pilot（2 场 = 4 次调用）
.venv-langgraph\Scripts\python.exe -m benchmarks.workflow.live_benchmark --limit 2 --max-calls 6
# 全量（25 场 = 50 次调用）
.venv-langgraph\Scripts\python.exe -m benchmarks.workflow.live_benchmark --max-calls 60
```

## 8. 局限

1. **25 场**是小样本，置信区间宽；不能外推为"生产准确率"。
2. 金标准是"作者标注 + 程序校验"，**未经第三方复核**。
3. 只有一种模型（deepseek-chat），没有横向对比。
4. 评分匹配器对"粒度/措辞"敏感，微 F1 偏向保守（§5）。
5. 邮件草稿质量**没有人评**：目前只验证"生成成功、有主题/正文、审批绑定版本"，没有评估邮件写得好不好。
